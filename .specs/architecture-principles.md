# Architecture Principles

**Status:** Draft · **Date:** 2026-07-25 · **Owner:** Ant Stanley · **Scope:** Repo-wide

This page defines **how** mason's code is organised: the crate graph, the seams,
the constraint that shapes every dependency choice, and the conventions each
language side follows. It is the canonical reference for "the engine", "the
seam", and "the platform layer" everywhere else in these specs.

---

## The organising constraint

**`mortar-core` must compile for `wasm32-unknown-unknown`.**

Nearly every non-obvious structural decision in the Rust half follows from this
one sentence. It is not a portability nicety: the default build mode *is* the
wasm one, so a dependency that fails on wasm32 is a dependency mason cannot use
at all.

What it rules out, and what stands in each place:

| Ruled out | What mason uses instead |
|---|---|
| A database, or any disk | In-memory `TtlCache`, exported to IndexedDB by the browser build |
| `moka` and other mature caches | A hand-rolled `HashMap` behind an async mutex |
| Threads, `Send` futures, `tokio::spawn` | `platform::spawn`, which is `spawn_local` on wasm |
| `std::time::Instant` / `SystemTime` | `web-time`, re-exported from `platform` |
| `tokio::time` | `gloo-timers` on wasm, behind `platform::sleep` / `timeout` |
| `reqwest` on the browser side | `gloo-net`, a thin wrapper over the fetch the worker already has |
| `governor`'s async wait | A hand-rolled check-then-sleep loop over the same `check()` |
| `std::net` resolution | Native-only DNS vetting; in the browser the fetch is the browser's |
| `rand`'s default features | `rand` and `rand_chacha` with `default-features = false` |

`rand` is the newest entry and the sharpest illustration. From 0.10 its default
features pull `getrandom`, which refuses to compile for
`wasm32-unknown-unknown` without an explicitly configured backend. mason never
needs OS entropy: the only RNG it builds is `ChaCha8Rng::seed_from_u64`, seeded
from the cursor. Turning the default features off drops `getrandom` and the
wasm build is clean again. **Do not restore them**; the failure is a hard
compile error in the default build mode.

That near-miss is why `just guard-wasm` exists. `lint` and `test` both run on
the host target, so with `rand`'s default features restored, clippy at
`-D warnings` passes and all 97 tests pass while the browser build is broken.
Only a wasm32 target build sees it, and `check` now runs one.

`reqwest` is worth naming specifically. It does build for wasm, but only as a
fetch wrapper, and it drags the `url` crate's IDNA and ICU tables in with it.
`gloo-net` does the same job without them.

Everything that differs between the two targets lives in `platform.rs` or behind
a `#[cfg(target_arch = "wasm32")]` inside `http.rs` and `pds.rs`. No other module
knows which target it is on.

## Crate graph

```
                    ┌──────────────────┐
                    │   mortar-core    │  the feed engine
                    │  native + wasm32 │
                    └────────┬─────────┘
                  ┌──────────┴──────────┐
                  ▼                     ▼
        ┌──────────────────┐   ┌──────────────────┐
        │  mortar-server   │   │   mortar-wasm    │
        │  axum binary     │   │  cdylib + rlib   │
        │  (server mode)   │   │  (local mode)    │
        └──────────────────┘   └────────┬─────────┘
                                        │  wasm-pack --target web
                                        ▼
                          web/src/lib/mortar-wasm/pkg  (gitignored)
                                        │
                          ┌─────────────┴─────────────┐
                          ▼                           ▼
                web/src/service-worker.ts     precached ?url asset
                          │
                          ▼
                web/src/routes + lib          the SPA
```

Rules:

1. **Both fronts are thin.** `mortar-server`'s feed route and `mortar-wasm`'s
   `feed_page` each do the same three things: parse the request into
   `(actor, cursor, Mode, FeedIntent)`, call `handle_feed`, and shape the result
   or the error for their transport. No feed logic lives in either.
2. **Nothing depends on a front.** `mortar-core` names neither axum nor
   wasm-bindgen.
3. **The web app depends on the wasm pkg, never on the crates.** The pkg is a
   build product, gitignored, regenerated by `just wasm`.
4. **The wire is the only contract between the halves**, and it is pinned by a
   fixture both sides check against (see [06](06-wire-contract.md)).

## Layering inside `mortar-core`

```
        feed.rs          the entry point; resolution and the owner gate
            │
            ▼
        algo/            what a wall IS
          snapshot.rs      state, admission, paging      ── the only mutex owner
          fill.rs          orchestration, fan-out, waves
          cohort.rs        who to ask
          mix.rs           what to lay next    ── pure
          score.rs         how good is it      ── pure
          cursor.rs        where are we        ── pure
            │
            ▼
        sources/         where content COMES FROM
          fetch.rs         the seam: one fetch-and-cache function per source
          bluesky.rs · pds.rs · standardsite.rs · streamplace.rs · util.rs
            │
            ▼
        http.rs          rate limiting, retry, backoff, timeout
        platform.rs      the native / wasm seam
        cache.rs         TTL storage        persist.rs   export / import
```

### What goes where

| Concern | Layer |
|---|---|
| Feed composition, ordering, admission | `algo/` |
| Anything that speaks an upstream wire format | `sources/` |
| Rate limiting, retry, backoff, request timeout | `http.rs` |
| Time, task spawning, sleeping | `platform.rs` |
| Storage lifetime and capacity | `cache.rs` |
| Serialising warm state across a worker death | `persist.rs` |
| HTTP routing, CORS, status codes | `mortar-server` |
| JS boundary types and throwing | `mortar-wasm` |

### The three rules that keep it honest

**1. `algo/` never names a source module.** Everything it needs comes through
`sources::fetch`, which returns bricks and the small set of yield types
re-exported from `sources/mod.rs`. `cache.rs` and `persist.rs` take those yield
types too, never a submodule directly. This is the **v2 seam**: swapping the
ingestion backend for a Jetstream plus SQLite design is meant to touch
`sources/` and nothing else.

**2. Every acquisition of a snapshot's inner mutex lives in
`algo/snapshot.rs`.** `fill` and `cohort` mutate the pool only through methods on
`Snapshot`, or not at all. `fill.rs` is orchestration; `cohort.rs` reads and
writes the shared activity cache and never sees a snapshot at all. Batched
admission (`admit_all`, `admit_repo_yield`) exists so a fan-out takes the lock
once per author rather than once per brick.

**3. Scoring and mixing are pure.** No clocks, no IO; `now` is always a
parameter. `lay(pool, wall, 20)` twice equals `lay(…, 40)` once, which is exactly
what makes an opaque `{seed, offset}` cursor sufficient.

## Layering in the web app

```
  routes/          URL to wall; nothing else routes
      │
      ▼
  lib/components/  presentation; no fetching except LandingWall's one demo call
      │
      ▼
  lib/state/*.svelte.ts   rune singletons; the only mutable app state
      │
      ▼
  lib/api.ts       the ONLY module that names /api/feed
      │
      ▼
  lib/types.ts     the wire mirror, guarded by contract-check.ts
```

Rules:

- **One module owns the network.** `api.ts` is the only place `/api/feed` appears
  outside the service worker, and the only place the build-mode switch is read.
- **State is singletons, not context.** Each `state/*.svelte.ts` exports one
  instance. `FeedState` is exported as a class as well, but only so tests can
  build throwaway instances; the app uses the singleton.
- **Components do not fetch.** The one exception is `LandingWall`, which asks for
  the demo wall behind the handle form and silently renders nothing if it fails.
- **The client re-implements no engine logic.** Ordering, dedup within a page,
  moderation and mixing are mortar's. The client's only dedup is a
  belt-and-braces pass across pages.
- **`colsForWidth` is the single source of column count**, measured on the
  container, so skeletons and laid bricks always agree.

## Failure philosophy

The engine degrades rather than erroring. Only four things produce an error
response at all: a missing `actor`, an unresolvable actor, a sealed wall, and a
load-bearing upstream failure during resolution. Everything downstream of that
returns an empty yield.

The corollary is that failures must be classified, not merely caught:

| Class | Cached? | Effect |
|---|---|---|
| Transient (transport, 429, 5xx, retries exhausted) | No | Asked again by the next wave or the next wall |
| Honest refusal (a plain 4xx, an empty collection) | Yes, as empty | Treated as a genuinely quiet author |

Caching a transient failure is the bug this exists to prevent: it silences an
author for a day over a blip.

## Security posture

mason is a logged-out reader with no credentials to leak, which removes a whole
class of concerns and sharpens the ones that remain.

| Concern | Where it is handled |
|---|---|
| Untrusted URLs reaching an `<a href>` | `sources/util.rs::is_http_url`, at every third-party url field |
| Query-string injection into upstream calls | `sources/util.rs::urlencode` on every interpolated value |
| SSRF via a hostile DID document | `sources/pds.rs`: scheme, userinfo, hostname, IP-literal and (natively) DNS vetting |
| Attacker-writable cursors | `checked_add` / `saturating_add` on the offset; garbage decodes to `None` |
| Hostile engagement counts | `saturating_add` / `saturating_mul` in `score::engagement` |
| Author-controlled timestamps | A 600 second future-skew allowance; beyond it, treated as unparseable |
| Cross-origin reads of the feed | An explicit CORS allowlist in server mode, never `*` |
| Moderation bypass | Label checks at the cohort, the live filter, and per post |

## Stack baseline

| Layer | Choice | Version |
|---|---|---|
| Rust | edition 2024, pinned channel | 1.97.0 |
| Async | tokio (native), `spawn_local` (wasm) | 1.x |
| HTTP server | axum + tower-http | 0.8 / 0.6 |
| HTTP client | reqwest + rustls (native), gloo-net (wasm) | 0.12 / 0.6 |
| Rate limiting | governor | 0.10 |
| Hashing | xxhash-rust (xxh3) | 0.8 |
| Seeded RNG | rand + rand_chacha | 0.9 |
| Frontend | SvelteKit, Svelte 5 runes, adapter-static | 2.x / 5.x |
| Styling | Tailwind v4, `@theme` tokens in CSS | 4.x |
| TypeScript | TS 7, `tsc --noEmit` | 7.x |
| Lint / format / dead code | oxlint, oxfmt, knip | not eslint or prettier |
| Video | hls.js, dynamically imported | 1.x |
| Package manager | pnpm | 11.x |
| Task runner | just | |

Two of these carry a caveat worth stating here rather than in a comment:

- **TypeScript 7, and it does not reach a component.** `svelte-check` crashes on
  TS 7 (its programmatic API stabilises in TS 7.1, around October 2026), so the
  typecheck is plain `tsc --noEmit`, which cannot parse `.svelte` and drops those
  files silently. `.ts` and `.svelte.ts` are fully checked; component bodies are
  checked by nothing. See
  [development-guidelines.md](development-guidelines.md) for what that costs and
  what covers the gap. Do not swap `check` back to `svelte-check` yet.
- **Runes are forced.** `vite.config.ts` sets `runes: true` for everything outside
  `node_modules`, so there is no legacy reactivity anywhere in the app.

## Assumptions and open questions

**Assumptions**

- `wasm32-unknown-unknown` remains the target; `wasm32-wasi` would relax several
  of the constraints above but is not what a browser runs.
- The dependency set stays wasm-compatible. Any new crate is a wasm question
  first and a feature question second.
- One deployable artefact remains the shape of the product, so a single version
  across the repo stays meaningful.

**Decisions**

- *One engine crate, two thin fronts.* **`mortar-core` compiles both ways.** A
  separate browser implementation would drift from the server one, and the whole
  claim that local mode is not a degraded mode rests on them being the same code.
- *`sources/` is a seam, not a folder.* **`fetch.rs` is the only door.** Naming a
  source module from `algo/` would make the v2 ingestion swap a rewrite instead
  of a replacement.
- *One mutex owner.* **Every lock acquisition is in `snapshot.rs`.** Lock
  discipline spread across three modules is how deadlocks and torn state arrive;
  keeping it in one file makes it reviewable.
- *Pure scoring and mixing.* **`now` is a parameter, never a call.** Determinism
  is what makes cursor pagination work and what makes the tests exact.
- *Degrade, do not error.* **Four error cases total.** One flaky PDS out of a
  hundred must not cost the reader their wall.
- *Classify failures.* **Transient is not cached; a refusal is.** Caching a blip
  silences an author for a day.
- *One network module in the web app.* **`api.ts`.** The build-mode switch and
  the service-worker readiness dance both need exactly one home.
- *State as singletons.* **One instance per module.** Svelte context would thread
  providers through a tree that has one route and no isolation requirement.
- *oxlint, oxfmt, knip.* **Not eslint or prettier.** Speed, and one toolchain
  family across the web side.

**Open questions**

- *The v2 ingestion seam is unproven.* `sources/` has one implementation. Whether
  the boundary is in the right place will only be known when a second one
  (Jetstream plus SQLite) is attempted.
- *Server mode has no consumer.* `mortar-server` is built, tested and deployable
  by hand, but nothing in the product requires it. The layering treats it as a
  first-class front; if it stays unused, that is cost without return.
- *Crate boundaries within `mortar-core`.* `algo`, `sources`, `http`, `cache` and
  `platform` are modules, not crates, so the layering rules are conventions rather
  than compiler-enforced. Open: is the enforcement worth the workspace churn?
