## Steps

- [ ] Add `RefreshWall.svelte`: a plain `<button type="button">` with a visible or `sr-only` accessible name, `min-h-11` for the 44px target, and a real `disabled` attribute bound to `feed.loading || feed.warming`.
- [ ] Call `reader.close()` before `feed.refresh()`, importing the reader singleton here rather than in `feed.svelte.ts`. Comment why the call lives at the control: a position in a list that is being replaced is not a position, and `reader.svelte.ts` already imports `feed.svelte.ts`, so the obvious placement is a cycle. Comment the second fact too, because it is easy to mistake this for dead code: with the reader open, task 03 marks the wrapper at `+layout.svelte:110` `inert`, and this control is inside it at `:128`, so today the state is unreachable through the only trigger. The call is the guarantee for the next trigger, not a live path.
- [ ] Scroll the wall to the top on click, using `behavior: 'auto'` when `matchMedia('(prefers-reduced-motion: reduce)').matches`, then call `feed.refresh()`.
- [ ] Resolve the scroll-versus-freeze interaction explicitly and comment the resolution in the file, covering **both** paths, because they are different bugs. The motion path: a programmatic scroll dispatches a scroll event, so a naive `scrollTo(); feed.refresh()` freezes the reflow it just started; either scroll only when already away from the top and defer `refresh()` past the scroll settling, or have the refresh suppress the first engage. The reduced-motion path: `FeedGrid.svelte:184` fires `freezeOnEngage()` with no scroll event at all, the instant `feed.warming` flips true, so nothing about the scroll resolution reaches it. Say plainly in the comment what a reduced-motion refresh therefore is, having **read task 25's guard rather than assuming it**: two cursorless requests go out (the preview `refresh()` issues synchronously, and the freeze the effect triggers), task 25's in-flight marker lets only the first carry `refresh=1`, the preview's page is discarded when the freeze bumps the generation, and the wall moves exactly once. One refreshed fan-out, no reflow. Task 27 copies whatever this comment says into `08`'s Refreshing paragraph, so a wrong sentence here becomes a wrong canonical page: neither "a single cursorless freeze" nor "a reflow" is what these readers get.
- [ ] Mount it in the `flex flex-nowrap` control row beside `LayoutPicker`.
- [ ] Decide the live-region question and record the decision: either give `FeedGrid` a refresh-aware branch (which needs `FeedState` to expose that this warm is a refresh) or let the existing "laying bricks" stand. Adding a second live region contradicts the page this control is being added to.
- [ ] Add `web/tests/refresh.test.ts` against the demo wall, at a 375px viewport.

## Definition of done

- [ ] The `disabled` attribute is real rather than a styled-off look, because it **is** the entire rate limit: a refresh costs one hundred-author AppView fan-out and there is no server-side throttle by design.
- [ ] The scroll-versus-freeze resolution is commented in the file for **both** paths and the motion path is asserted by the Playwright case, not left to the implementer of the next change. The reduced-motion path is a written statement, not an assertion: two cursorless requests, one of them carrying the flag because of task 25's in-flight marker, and one movement of the wall. The count is read out of task 25's vitest race case rather than reasoned about here, and task 27 records it in `08`.
- [ ] `web/tests/refresh.test.ts` asserts: the control renders with an accessible name at 375px; clicking it leaves bricks on the wall (`#wall article` stays visible, the skeleton grid never appears); the control is `disabled` while warming and enabled once settled; a second click while disabled starts nothing.
- [ ] The disabled-window assertion uses the **one** mechanism that can see it, and says in the spec file why it is the only one. `feed.rs:60` answers a demo preview with `warming: false`, so `#warm` freezes on its first poll and the window is roughly two service-worker round trips: a plain `await expect(button).toBeDisabled()` can arrive after it closed and pass or fail on timing. The mechanism is a synchronous read: one `page.evaluate` that clicks the control and reads its `disabled` property in the same evaluated function, before yielding to the event loop. Delaying `/api/feed` with `context.route` is **not** an option and the file says so: `service-worker.ts:290`-`:296` answers that path with `event.respondWith(serveFeed(...))` out of wasm, and on the demo wall the bricks are fixtures compiled into the binary, so there is no network request to delay and a page-to-worker request is not routable. A flaky assertion on the control that **is** the rate limit is worse than no assertion, because it will be deleted rather than fixed.
- [ ] The reader close is in the click handler, ahead of `feed.refresh()`, and `grep -n "reader" web/src/lib/state/feed.svelte.ts` returns nothing, which is the other half of the same decision. The Playwright spec does not assert it: with the reader open this control sits inside task 03's `inert` wrapper and cannot be clicked, and the spec file says so.
- [ ] The spec file notes honestly that the demo wall ignores `refresh` in the engine, so this lane covers the **client** behaviour and not the re-read, which tasks 20 and 22 cover in `cargo nextest`.
- [ ] Meets the repo definition of done, and the PR states that `just check` does **not** cover this task's deliverable: `just build && cd web && pnpm test:e2e` is the lane, and CI's `e2e` job is the enforcement point.
- [ ] Reviewable: `just build && cd web && pnpm test:e2e`, then open the built site at 375px and press the control twice quickly.
