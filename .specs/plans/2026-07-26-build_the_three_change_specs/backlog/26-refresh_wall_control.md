## Steps

- [ ] Add `RefreshWall.svelte`: a plain `<button type="button">` with a visible or `sr-only` accessible name, `min-h-11` for the 44px target, and a real `disabled` attribute bound to `feed.loading || feed.warming`.
- [ ] Call `reader.close()` before `feed.refresh()`, importing the reader singleton here rather than in `feed.svelte.ts`. Comment why the call lives at the control: a position in a list that is being replaced is not a position, and `reader.svelte.ts` already imports `feed.svelte.ts`, so the obvious placement is a cycle. Comment the second fact too, because it is easy to mistake this for dead code: with the reader open, task 03 marks the wrapper at `+layout.svelte:110` `inert`, and this control is inside it at `:128`, so today the state is unreachable through the only trigger. The call is the guarantee for the next trigger, not a live path.
- [ ] The click handler calls `reader.close()` and `feed.refresh()`, and **does not scroll at all**. No `scrollTo`, no `scrollIntoView`, no anchor jump.
- [ ] Comment why there is no scroll, because it looks like an omission. `FeedGrid.svelte:181` is one `$effect` whose first statement is `if (!feed.warming) return;`, so on a settled wall **no** freeze listener exists and the "scroll first and you freeze the wall" hazard an earlier draft described cannot fire. The real coupling is event delivery and it is symmetric: `refresh()` flips `warming` true synchronously, the effect re-runs on a microtask and attaches the `{passive, once}` scroll listener at `:191`, and the `scroll` event queued by `window.scrollTo` is delivered *after* that microtask. `freeze()`'s guard at `feed.svelte.ts:124` rejects only when `!warming || loading`, and `refresh()` sets neither, so **either** call order commits the wall on its own programmatic scroll with no reflow. Not scrolling removes the coupling instead of timing around it. **The reduced-motion path** is reachable from no scroll ordering at all: `FeedGrid.svelte:184` calls `freezeOnEngage()` the instant `feed.warming` flips true, with no listener and no scroll event. Say plainly in the comment what a reduced-motion refresh therefore is, having **read task 25's guard rather than assuming it**: that freeze is **deferred**, because task 25's in-flight marker makes `freeze()` return early while the flagged cursorless preview is still in flight, so exactly **one** cursorless request goes out under the refresh; when the preview lands, `#warm` has adopted its cursor (which carries the refreshing snapshot's seed) and freezes from there, so the request that commits lands on the refreshed wall. One refreshed fan-out, and one reflow when the preview lands rather than a commit before the wall moves. Task 27 writes that sentence into `08`'s Refreshing paragraph from this comment (the rest of that paragraph is the block's own prose), so a wrong sentence here becomes a wrong canonical page: "two cursorless requests, one of them flagged" is the mechanism this plan **replaced** (the unflagged one commits the pre-refresh wall off warm caches), and "no reflow at all" is not what these readers get either.
- [ ] Mount it in the `flex flex-nowrap` control row beside `LayoutPicker`.
- [ ] Add **no** live region, which the change spec settles rather than leaves open: the wall keeps its single polite region at `FeedGrid.svelte:221`, which already says "laying bricks" while warming, and a refresh is a warm, so it needs no new announcement. Record that in the file as a decision so the next reader does not rediscover it, and do not give `FeedGrid` a refresh-aware branch either: `08`'s accessibility section states there is exactly one region for the whole wall, and a second would contradict the page this control is being added to.
- [ ] Add `web/tests/refresh.test.ts` against the demo wall, at a 375px viewport.

## Definition of done

- [ ] The `disabled` attribute is real rather than a styled-off look, because it **is** the entire rate limit: a refresh costs one hundred-author AppView fan-out and there is no server-side throttle by design.
- [ ] The click handler contains no scroll call of any kind, and a comment says why (either order freezes the wall on its own programmatic scroll, because the queued `scroll` event is delivered after the microtask that arms the listeners). The reduced-motion path is a written statement, not an assertion: one cursorless request, because task 25's in-flight marker defers the freeze the effect triggers, and a commit that rides the cursor `#warm` adopted from the flagged preview. The mechanism is read out of task 25's vitest race case rather than reasoned about here, and task 27 records it in `08`.
- [ ] `RefreshWall` adds no live region: `grep -n 'aria-live' web/src/lib/components/RefreshWall.svelte` returns nothing, `FeedGrid.svelte:221` is still the wall's only one, and `FeedGrid` gained no refresh-aware branch. The change spec settles this, so a decision recorded the other way is a divergence rather than a judgement call.
- [ ] `web/tests/refresh.test.ts` asserts: the control renders with an accessible name at 375px; clicking it leaves bricks on the wall (`#wall article` stays visible, and the twelve-card `initialLoad` grid never appears; the four-card warming tail at `FeedGrid.svelte:361` **does** appear and is expected); the control is `disabled` while warming and enabled once settled; a second click while disabled starts nothing.
- [ ] The disabled-window assertion uses the **one** mechanism that can see it, and says in the spec file why it is the only one. `feed.rs:60` answers a demo preview with `warming: false`, so `#warm` freezes on its first poll and the window is roughly two service-worker round trips: a plain `await expect(button).toBeDisabled()` can arrive after it closed and pass or fail on timing. The mechanism is a synchronous read: one `page.evaluate` that clicks the control and reads its `disabled` property in the same evaluated function, before yielding to the event loop. Delaying `/api/feed` with `context.route` is **not** an option and the file says so: `service-worker.ts:290`-`:296` answers that path with `event.respondWith(serveFeed(...))` out of wasm, and on the demo wall the bricks are fixtures compiled into the binary, so there is no network request to delay and a page-to-worker request is not routable. A flaky assertion on the control that **is** the rate limit is worse than no assertion, because it will be deleted rather than fixed.
- [ ] The reader close is in the click handler, ahead of `feed.refresh()`, and `grep -n "reader" web/src/lib/state/feed.svelte.ts` returns nothing, which is the other half of the same decision. The Playwright spec does not assert it: with the reader open this control sits inside task 03's `inert` wrapper and cannot be clicked, and the spec file says so.
- [ ] The spec file notes honestly that the demo wall ignores `refresh` in the engine, so this lane covers the **client** behaviour and not the re-read, which tasks 20 and 22 cover in `cargo nextest`.
- [ ] Meets the repo definition of done, and the PR states that `just check` does **not** cover this task's deliverable: `just build && cd web && pnpm test:e2e` is the lane, and CI's `e2e` job is the enforcement point.
- [ ] Reviewable: `just build && cd web && pnpm test:e2e`, then open the built site at 375px and press the control twice quickly.
