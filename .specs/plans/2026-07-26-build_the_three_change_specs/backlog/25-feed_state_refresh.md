## Steps

- [ ] Add `refresh()`, refusing without side effects while `loading`, while `warming`, or with no target, mirroring `loadMore`'s guard.
- [ ] Delete this target's `#cache` entry **before** bumping the generation, so a later `reset` for the same key cannot rehydrate the wall the reader just replaced.
- [ ] Set `cursor = null`, `done = false`, `warming = true`, bump `#generation`, arm a private refresh flag, and spawn `#warm(generation)`. Do **not** touch `items` and do **not** set `initialLoad`.
- [ ] Do **not** import `reader.svelte.ts` here. Closing an open reader is the right behaviour for the same reason `refresh()` refuses while warming (a position in a list that is being replaced is not a position), but the call belongs at the trigger: `reader.svelte.ts` already imports this module, so the reverse import is a cycle, and it would put `$app/navigation` and `$app/state` in `feed.test.ts`'s graph. Task 26 calls `reader.close()` before `feed.refresh()`. If a second trigger for `refresh()` ever appears, it inherits that ordering rather than this module inheriting the import.
- [ ] Guard the **cost**, not just the flag, with a second private marker: at most one in-flight request may carry `refresh=1` per refresh. `#warm`'s first `fetchFeed` is issued synchronously by `refresh()` with `this.cursor === null`, and `freeze()` at `:121` proceeds while `warming` is true and `loading` is false, with its own null cursor, so without the marker two cursorless requests go out under one tap. Each rolls its own `fresh_seed`, inserts its own snapshot and spawns its own fill, so honouring the flag on both is two hundred-author fan-outs from one tap, which is precisely what "the control is the rate limit" says cannot happen. The rule in three lines: write the flag into a request only when it is armed **and** nothing carrying it is in flight; clear the in-flight marker when that request settles, adopted or not; disarm the flag when the wall settles (`freeze`'s `finally` with the generation matching) or on the next `reset`, so it can never leak into a later wall.
- [ ] Say in a comment what the guard buys, because it is not obvious: in the freeze-beats-preview race the flagged preview is discarded, but its fan-out has already re-read `author_feed` and `image_feed`, so the freeze that supersedes it reads the entries the refresh just overwrote. The reader gets fresh bricks from an unflagged request. This is why the guard drops the second flag rather than moving it.
- [ ] Update `feed.test.ts:106`-`:110` and `:159` for the new argument, leaving `loadMore`'s assertion at its current length.
