## Steps

- [ ] Add `refresh()`, refusing without side effects while `loading`, while `warming`, or with no target, mirroring `loadMore`'s guard.
- [ ] Delete this target's `#cache` entry **before** bumping the generation, so a later `reset` for the same key cannot rehydrate the wall the reader just replaced.
- [ ] Set `cursor = null`, `done = false`, `warming = true`, bump `#generation`, arm a private refresh flag, and spawn `#warm(generation)`. Do **not** touch `items` and do **not** set `initialLoad`.
- [ ] Do **not** import `reader.svelte.ts` here. Closing an open reader is the right behaviour for the same reason `refresh()` refuses while warming (a position in a list that is being replaced is not a position), but the call belongs at the trigger: `reader.svelte.ts` already imports this module, so the reverse import is a cycle, and it would put `$app/navigation` and `$app/state` in `feed.test.ts`'s graph. Task 26 calls `reader.close()` before `feed.refresh()`. If a second trigger for `refresh()` ever appears, it inherits that ordering rather than this module inheriting the import.
- [ ] Guard the **cost** with a second private marker, and make the marker **defer** the second cursorless request rather than send it stripped of the flag. `#warm`'s first `fetchFeed` is issued synchronously by `refresh()` with `this.cursor === null`, and `freeze()` at `:121` proceeds while `warming` is true and `loading` is false, with its own null cursor, so without the marker two cursorless requests go out under one tap. Each rolls its own `fresh_seed`, inserts its own snapshot and spawns its own fill, so honouring the flag on both is two hundred-author fan-outs from one tap, which is precisely what "the control is the rate limit" says cannot happen. The rule in three lines: `refresh()` arms the flag **and** sets the in-flight marker; while the marker is set, `freeze()` returns early with no side effect at all, beside the existing guard at `:124` and ahead of `#generation++` and `loading = true`, so the second cursorless request is held rather than issued; clear the marker when the flagged request settles, adopted or not, and disarm the flag when a cursorless response is adopted, when the wall settles (`freeze`'s `finally` with the generation matching) or on the next `reset`, so it can never leak into a later wall. The deferred commit is not lost: once the preview resolves, `#warm` has adopted its cursor, which carries the refreshing snapshot's seed, and `#warm` freezes from there itself when the snapshot settles or the ceiling hits.
- [ ] Say in a comment why the second request is deferred rather than merely unflagged, because the two look equivalent and only one works. A cursorless request rolls a fresh seed and spawns a second, **unflagged** fill, and that fill is answered from the still-valid five-minute `author_feed` entries without a single network call, so it clears its first-paint bar (`FIRST_PAINT_AUTHORS`, 12 distinct authors) at once while the flagged fill is still working through up to a hundred rate-limited AppView calls. The unflagged request is therefore the one that commits, and what it commits is the wall from **before** the refresh. Deferring means the request that commits is the one carrying the refreshing snapshot's cursor. Under `prefers-reduced-motion: reduce` this is the ordinary path rather than a race (`FeedGrid.svelte:184` freezes the instant `warming` flips true, with no scroll event at all), so it is what those readers get every time, and the cost of the deferral for them is that the wall reflows once when the preview lands instead of committing before it moves.
- [ ] Update `feed.test.ts:106`-`:110` and `:159` for the new argument, leaving `loadMore`'s assertion at its current length.

## Definition of done

- [ ] A vitest case proves the outgoing wall stays on screen: after `refresh()` and before the first preview resolves, `items` is unchanged, `initialLoad` is false and `warming` is true.
- [ ] A vitest case proves the flag is sent exactly once across a preview-plus-freeze cycle.
- [ ] A vitest case drives the freeze-beats-preview race directly (`refresh()`, then `freeze()` before the first preview's promise resolves) and asserts the **committed** request, not only the count: over the whole mock call list at most one call carries `refresh=1`, **and** the call that commits (the `"freeze"` one) either carries `refresh=1` or carries a non-null cursor. The second half is the half that matters. A count on its own is green on the broken behaviour, where the freeze goes out cursorless and unflagged, satisfies "exactly one flagged call", and commits the pre-refresh wall off warm caches while the flagged fill is still fanning out. This assertion is what stands between one tap and either two hundred-author fan-outs or a refresh that visibly does nothing.
- [ ] A vitest case proves the flag cannot leak: after a refresh settles, a later `reset` on the same instance sends no `refresh=1`.
- [ ] A vitest case proves the session-cache entry is dropped: refresh, settle, then `reset` on the same target rehydrates the **new** wall, and a `reset` issued while the refresh is still warming does not resurrect the old one.
- [ ] A vitest case proves `refresh()` is a no-op while warming, so a double call cannot start two fan-outs.
- [ ] `refresh()` touches no DOM and imports no reader: closing the reader is task 26's job, and nothing scrolls anywhere in a refresh (task 26's control does not scroll either, for the reasons recorded there). That is what keeps this module runnable in vitest's node environment.
